# Нативное сравнение CEL-C++ и ExprTk, 2026-10-23

## Граница поставки

Исследовательский стенд находится в
[`tests/expression_native`](../../tests/expression_native/README.md), отдельно
от production-библиотек, default build и установленного пакета Forge.
Основа рабочей ветки `expression-native-comparison-v1` — Forge
`e51c6929fd120d13976963e9d633ba77b3044e01`. Код стенда является отдельным
рабочим изменением, а не частью этого базового коммита.

Проверяется пригодность нативных кандидатов для будущего ограниченного
вычислителя. Новый parser, AST — синтаксическое дерево — evaluator или
числовой тип здесь не реализуются. Калькулятор, контрактные интринсики,
тарифный реестр и расчётные контракты этой поставкой не добавляются.
Наличие WAMR в базовом Forge не превращает данный нативный эксперимент
в проверку контрактного исполнения Spine/WAMR.

## Результат запуска

На macOS ARM64 выполнены 69 случаев для каждого кандидата, всего 138
отдельных процессов. Для девяти сценариев: 1000 прогревочных вычислений,
семь выборок по 10000 вычислений. Оба кандидата собраны Homebrew LLVM 22.1.8,
C++23, с эффективными `-O2 -g0 -fno-fast-math -ffp-contract=off`.

| Кандидат | Совпадения с точным эталоном/ожидаемым отказом | Расхождения | Ошибки стенда |
| --- | ---: | ---: | ---: |
| CEL, проверенный int64-профиль | 67 | 2 | 0 |
| ExprTk, проверенный double-профиль | 54 | 15 | 0 |

Это не итоговая оценка безопасности или процент production-готовности.
В корпус входят проверки разных возможностей и настроенных лимитов;
пять расхождений ExprTk связаны с формой вектора, два — с отсутствием того же
comprehension counter, остальные — с арифметикой и отсутствующим ключом.
Часть численно корректных результатов ExprTk не доказывает общую точность double.

## Наблюдения о корректности и ограничениях

### CEL-C++

- Проверяемые `int64` сохраняют `9007199254740993`, возвращают ошибки
  переполнения и нулевого делителя. Успешный `StatusOr<Value>` может содержать
  CEL ErrorValue; адаптер проверяет оба пути.
- В проверенном int64-профиле промежуточное произведение может переполниться,
  хотя итог после деления помещается в диапазон. Корпус содержит два таких
  случая: масштабирование `10^15 × 9999 / 10000` и произведение `10^30`.
  Первый product помещается в uint64, второй — нет. Отдельный uint64-профиль
  и финансовые extensions — расширения — этой проверкой не квалифицированы.
  Для общего финансового профиля требуется отдельно проверить достаточный
  диапазон или точную функцию с широким промежуточным значением, сохраняя
  overflow checks.
- `comprehension_max_iterations=1024` имеет исключающую границу в проверенном
  runtime: 1023 элемента проходят, 1024 и 1025 отклоняются. Эти случаи явно
  отделены от донорских формул. ExprTk не предоставляет тот же счётчик.
- Глубокие и сложные выражения в корпусе первыми достигают parser recursion
  limit 64. Отдельное фактическое срабатывание node limit 4096 этим не доказано.
- Общего полного бюджета памяти и нативной работы текущий адаптер не реализует.
  Подключена standard library, а не принятый финансовый allowlist — список
  разрешённых типов и операций. Это не готовый sandbox для недоверенных программ.

### ExprTk

- Native `double` теряет точность выше `2^53`; переполнение `int64` само по себе
  не становится ошибкой. `NaN` и infinity от арифметики остаются значениями
  движка, а не маскируются под его диагностический отказ.
- Отдельная настоящая компиляция `parser<long long>` завершается ошибкой
  upstream numeric dispatch. Это не готовая штатная целочисленная замена.
- В проверенном профиле `swap(x,y)` и `x <=> y` принимаются и меняют входы,
  несмотря на immutable symbol table и отключённые assignment operations.
  Это ограничение выбранного профиля, не утверждение об уязвимости любого
  применения ExprTk. Собственный фильтр синтаксиса в стенд не добавлялся.
- `if`, `?:`, `&` и `|` показали ленивое поведение с диагностической функцией,
  считающей вызовы; словесные `and` и `or` вызывают её в обеих ветвях теста.
  Диагностическая функция отсутствует в измеряемом backend.
- При включённом strength reduction наблюдаются другие результаты крайних
  выражений: конечное среднее становится infinity, вложенное деление — нулём.
  Измеряемый профиль отключает это преобразование.
- Parser stack limit, unary depth limit и compilation checkpoints срабатывают.
  В отдельном тесте вложенные ternary принимаются при меньшем node depth limit;
  универсальность этого ограничения не подтверждена.
- Пустой вектор нельзя зарегистрировать выбранным API. Обращение к постоянному
  индексу вне известной длины отвергается ещё при компиляции, даже если ветвь
  защищена условием. Это ограничение формы вектора/выражения, а не отсутствие
  ленивого вычисления при исполнении.

## Что означают замеры

Подготовка программы измеряется отдельно от её повторного исполнения.
Переменные не объявлены compile-time constants. CEL использует fresh arena
для каждой оценки, чтобы память не росла от накопления результатов. Общая
сборка scalar result и checksum включены в оба пути; печать вынесена из цикла.

Представления формул и число операций различаются: CEL использует целочисленные
quotient/remainder, ExprTk — штатные `ceil`/`floor`. Поэтому измеряется стоимость
этих сценариев, а не универсальный коэффициент скорости. Peak RSS относится
ко всему процессу с библиотеками, не к памяти отдельной формулы и не к hard cap.
Фоновая нагрузка всей пользовательской машины не контролировалась.

Ошибки процесса, отсутствие метрик и несовпадение встроенного хеша корпуса
считаются HARNESS_ERROR — ошибкой стенда. Ожидаемая арифметическая ошибка
не может быть подтверждена ошибкой разбора. Кандидаты с несовпадениями не
объявляются прошедшими финансовую приёмку по одному успешному запуску стенда.

## Вывод и следующая граница

Для следующего нативного прототипа предпочтителен CEL-C++: в нём уже есть
проверяемая целочисленная арифметика, типизация и разделение parser/checker/runtime.
Это рекомендация исследования, не принятие production-зависимости.
Штатный ExprTk удобен как быстрый вещественный вычислитель, но для данной
задачи требует существенно более глубоких изменений арифметики и ограничений.

Следующий предлагаемый срез — ограниченный нативный профиль на штатных CEL API:
точные нужные финансовые функции, бюджет всех разрешённых операций и памяти,
версионированное представление программы. Только после его проверки — SDK и
интринсики в существующем Forge testing host. Расположение этих компонентов
и публичные API определяются отдельным решением, без преждевременных фасадов.

Linux, кроссплатформенная воспроизводимость, контрактный WASM, ресурсы Spine,
выплаты и реальные запросы к провайдерам здесь NOT_RUN. Экономика и ставки
из этого сравнения не выводятся.
